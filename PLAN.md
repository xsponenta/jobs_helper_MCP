# План: мультиагентна система «Пошук вакансій, відгук і профіль кандидата»

Міні-проєкт «Два агенти й інструмент, якого в них не було» (див. `Mini Project Agents MCP.pdf`).
Робимо поетапно: кожен етап закінчується перевіркою «готово», і тільки потім переходимо до наступного.

## Ідея
Кандидат дає своє CV і запит, наприклад «знайди remote Python-вакансії від $3000 і відгукнись на дві найкращі».
Система:
1. **Шукає вакансії** на DOU, Djinni і Happy Monday.
2. **Адаптує CV і cover letter** під кожну вакансію, не вигадуючи фактів.
3. **Відгукується** від імені кандидата через його власну сесію в браузері.
4. **LinkedIn:** готує й публікує пости (офіційне API) і пропонує оновлення профілю.

## Що можливо на кожній платформі (перевірено)

| Платформа | Пошук | Відгук | Профіль | Як робимо |
|---|---|---|---|---|
| **DOU** | ✅ офіційний RSS `jobs.dou.ua/vacancies/feeds/?category=…&exp=…` | ⚠️ API немає | ⚠️ API немає | RSS для пошуку, Playwright із сесією кандидата для відгуку. Якщо вакансія веде на сайт компанії, переходимо туди, визначаємо форму (відомий ATS чи невідомий сайт) і заповнюємо її, якщо це можливо (див. «Зовнішні форми») |
| **Djinni** | ✅ RSS `djinni.co/jobs/rss/?primary_keyword=…` | ⚠️ API немає | ⚠️ API немає | RSS + Playwright. **Перший сайт для відгуку**: форма на самому сайті |
| **Happy Monday** | ⚠️ API і RSS немає: `job-sitemap.xml` + HTML сторінок `/jobs/<id>` | ⚠️ API немає | ⚠️ API немає | Sitemap і парсинг з кешем, відгук через Playwright, зовнішні форми так само, як на DOU |
| **LinkedIn** | ❌ не робимо | ❌ не робимо | ❌ запис через API неможливий | **Пости:** офіційне API (`w_member_social`). **Профіль:** агент генерує готовий текст, кандидат вставляє сам |

### Зовнішні форми (сайт компанії / ATS)
Коли кнопка «Відгукнутися» веде за межі DOU / Djinni / Happy Monday, `apply` не здається, а йде за посиланням:

1. **Визначає тип форми** за доменом і DOM:
   - **відомий ATS:** Greenhouse, Lever, Workable, PeopleForce, Recruitee, SmartRecruiters, Teamtailor, BambooHR — точний список складемо на етапі 1 зі статистики;
   - **невідома форма** на сайті компанії;
   - **не форма:** email, Telegram, Google Form з логіном, сторінка без форми.
2. **Витягує схему форми:** поля з підписами (label), типом, обов'язковістю, варіантами відповіді і полем для файлу CV.
3. **Автоматично заповнює відомі поля** з `candidate.yaml` (ім'я, email, телефон, посилання, місто, очікувана зарплата, термін виходу, дозвіл на роботу), CV у PDF і cover letter.
4. **Решту обов'язкових полів не вигадує.** Повертає агенту `needs_input` зі списком питань: «Скільки років досвіду з Kafka?», «How did you hear about us?». Перевіряльник відповідає з CV або `candidate.yaml` і повторює `apply(..., answers={...})`. Якщо відповіді в даних немає, питання йде людині.
5. **Не заповнює, а повертає посилання** (`external_apply`), якщо форма потребує логіну на сайті компанії, має капчу, багатокрокова без схеми або це не форма взагалі. Для email-відгуку можна запропонувати чернетку листа.

Чутливі питання (дозвіл на роботу, віза, судимість, згода на обробку даних) агент **ніколи не заповнює сам**, тільки з `candidate.yaml` або після підтвердження людиною.

Публічні API самих ATS (наприклад, Greenhouse Job Board API для подання заявок) потребують ключа роботодавця, тож для кандидата лишається тільки браузер.

Принципи:
- **Пароль ніколи не потрапляє до агента.** Кандидат логіниться сам у вікні браузера, сесія зберігається в локальному профілі.
- **Як відправляти, вирішує людина, окремо для кожного сайту** (див. «Політика відправки»). Агент не може змінити цей вибір.
- **Скрейпінг ввічливий:** мало запитів, кеш, дотримання `robots.txt`.

## Стек
- **Python 3.13 + uv**, у `pyproject.toml` прописати `[tool.uv] package = false`.
- **MCP:** офіційний `mcp` SDK 2.x. У 2.x `FastMCP` перейменовано на `MCPServer` (`from mcp.server.mcpserver import MCPServer`). Транспорт stdio.
- **Агенти:** `claude-agent-sdk`. Працює через звичайний логін у Claude, API-ключ не потрібен.
- **Парсинг:** `httpx` + `feedparser` для RSS, `selectolax` або `beautifulsoup4` для HTML.
- **Браузер:** `playwright` із persistent context, окремий профіль на кожного кандидата. Ним же рендеримо CV з markdown у PDF (`page.pdf()`).
- **LinkedIn:** OAuth 2.0 (OpenID Connect + Share on LinkedIn), Posts API.
- **Трейсинг:** JSONL через хуки Agent SDK і аудит-лог на стороні MCP-серверів.

## Архітектура

```
                 ┌────────────── оркестратор (Python) ──────────────┐
User + CV ──►    │  Скаут (A)  ──чернетки──►  Перевіряльник (B)     │ ──► відповідь
                 │  read-only                  ЄДИНИЙ, хто пише     │
                 └────┬────────────────────────────┬───────────────┘
                      │ search_jobs, get_job       │ get_job, apply, publish_post
                      ▼                            ▼
              MCP `jobs`                     MCP `jobs` (apply) / MCP `linkedin` (publish_post)
              ├─ DOU RSS                     ├─ Playwright + сесія кандидата → DOU / Djinni / HM
              ├─ Djinni RSS                  ├─ applications.csv (трекер) + скриншоти
              └─ Happy Monday sitemap+HTML   └─ LinkedIn Posts API (OAuth токен кандидата)
```

**MCP-сервер `jobs`** — основний, оцінюється за вимогами (3 інструменти):

| Інструмент | Що робить | Стан |
|---|---|---|
| `search_jobs(query, sources?, work_mode?, min_salary?, seniority?, limit?)` | агрегований пошук по 3 сайтах, нормалізовані вакансії | читає |
| `get_job(job_id)` | повний текст і вимоги вакансії, тип відгуку (`on_site` / `external_ats:<name>` / `external_form` / `external_other`) | читає |
| `apply(job_id, cv_markdown, cover_letter, answers?)` | рендерить CV у PDF, заповнює форму на сайті або на зовнішньому ATS, на невідомі обов'язкові поля повертає `needs_input`, робить скриншот і далі діє за політикою відправки цього сайту; пише в трекер | **пише** |

**MCP-сервер `linkedin`** — розширення (2 інструменти):

| Інструмент | Що робить | Стан |
|---|---|---|
| `get_profile()` | ім'я, фото, email кандидата (OpenID `userinfo`), статус токена | читає |
| `publish_post(text, visibility)` | публікує пост від імені кандидата через Posts API за політикою відправки для `linkedin`; у `dry_run` тільки валідує і зберігає | **пише** |

Оновлення профілю LinkedIn — **не інструмент, а результат роботи агента**: файл `profile_update.md` з заголовком, «About», навичками та пунктами досвіду. Кандидат вставляє його вручну. API для запису профілю LinkedIn не надає.

**Формат помилки** (однаковий для всіх інструментів):
```json
{"error": "not_logged_in", "message": "Сесія Djinni відсутня або прострочена.",
 "hint": "Запусти `uv run python -m cli login djinni` і увійди в акаунт.", "retryable": false}
```
Коди:
- спільні: `invalid_argument`, `job_not_found`, `job_closed`, `forbidden`, `internal_error`;
- відгук: `already_applied`, `not_logged_in`, `captcha_required`, `needs_input` (зі списком полів), `external_apply` (посилання, коли форму заповнити неможливо), `form_changed`, `cv_too_long`;
- LinkedIn: `token_expired`, `post_too_long`, `rate_limited`.

**Політика відправки** — вибір людини, окремо для кожного сайту. Зберігається в `settings.yaml` (у `.gitignore`):
```yaml
submit_policy:
  dou: manual          # manual | confirm | auto
  djinni: confirm
  happymonday: confirm
  ats: confirm         # усі зовнішні сайти компаній / ATS
  linkedin: confirm    # пости
```
- `manual` — агент заповнює форму у видимому браузері й зупиняється, «Надіслати» натискає людина. Інструмент чекає, поки на сторінці з'явиться підтвердження відправки, або поки людина закриє вікно, і записує в трекер `submitted` чи `abandoned`.
- `confirm` — агент заповнює форму, і просто у вікні браузера з'являється панель «Надіслати / Скасувати»; на «Надіслати» агент натискає кнопку відправки сам. Питання в консолі неможливе: MCP-сервер працює як підпроцес агента, і його stdio зайнятий протоколом.
- `auto` — агент відправляє без питань.

Як це працює:
- **Перший відгук на сайт без збереженої політики.** CLI питає людину, показує коротку довідку про правила сайту і зберігає вибір. Для DOU довідка цитує заборону автоматичних відгуків з `dou.ua/applications-rules`.
- **Значення за замовчуванням:** DOU — `manual`, решта — `confirm`. Вибір можна змінити: `cli policy set dou auto`.
- **Агент не може обійти політику.** `apply` і `publish_post` не мають параметра режиму, MCP-сервер сам читає `settings.yaml`.
- **Глобальний `--dry-run`** (`JOBS_DRY_RUN=1`) перекриває всі політики: заповнити, зробити скриншот, нічого не відправляти. Він використовується для оцінки, тестів і репетицій.
- **Статуси в трекері:** `prepared` (dry run), `awaiting_user`, `submitted`, `declined` (людина сказала «ні»), `abandoned`, `failed`.

**Бекенди `apply`:**
- `browser` — справжні сайти, для демо;
- `mock` — локальна імітація форми з тими самими помилками, для оцінки й тестів.

  - `confirm`: панель «Надіслати / Скасувати», вбудована в сторінку (реалізація `Confirmer` для браузера).

**Готово, коли:**
- на Djinni `dry_run` стабільно заповнює форму зі скриншотом 3 рази поспіль;
- кожна з трьох політик (`manual`, `confirm`, `auto`) перевірена хоча б на одній свідомій справжній заявці;
- для щонайменше 2 зовнішніх ATS `dry_run` заповнює форму, а невідомі питання повертаються як `needs_input`.

## Етап 5. MCP-сервер `linkedin` — ✅ зроблено (без справжнього токена)

Реалізація: `jobs_helper/linkedin/` (OAuth, сервіс), `jobs_helper/mcp_linkedin/server.py`, тести на змоканому API `tests/test_linkedin.py`.

- **Політика `manual`** відкриває вікно публікації LinkedIn з уже вставленим текстом (UI LinkedIn не автоматизуємо).
- **Справжній пост перевіримо після створення LinkedIn-застосунку** (`.secrets/linkedin.env`).
- **Агенти:** Скаут має `get_profile`, Перевіряльник — `publish_post` і `save_profile_update`. Додано кейс оцінки `c6_linkedin`.
- **Підключення до Claude Code:** `.mcp.json`; інструкція для Claude Desktop — у README.
- `cli login linkedin`: локальний OAuth-флоу (redirect на `localhost`), токен зберігається в `.secrets/linkedin.json`. Токен живе близько 60 днів, `token_expired` пояснює, як оновити.

  - `confirm` — «так / ні»;
  - `auto` — публікувати одразу.

  `--dry-run` тільки зберігає чернетку в `linkedin_posts.csv`.

**Готово, коли:** `dry_run` проходить через MCP-клієнт, і **один** справжній тестовий пост опубліковано (можна з видимістю `CONNECTIONS`).

## Етап 7. Два агенти (1 бал) — ✅ зроблено

Реалізація: `jobs_helper/agents/prompts.py`, `jobs_helper/agents/orchestrator.py`, CLI `jobs_helper/agents/run.py`.
- **Секція `sensitive` з `candidate.yaml` агентам не передається:** її бачить тільки MCP-сервер.
**A. Скаут** (`search_jobs`, `get_job`, `get_profile`). Писати не може.
- Розбирає обмеження запиту: сайти, тип роботи, зарплата, скільки заявок, чи взагалі відгукуватись.
- Шукає, ранжує за відповідністю CV.
- Готує адаптоване CV, cover letter, а на запит ще й текст LinkedIn-поста і `profile_update.md`.
- **Правило правдивості:** тільки факти з базового CV. Прогалини записує в `gaps`, а не в CV.

**B. Перевіряльник** (`get_job`, `apply`, `publish_post`). **Єдиний, хто пише.**
- Перевіряє:
  - відповідність запиту;
  - вакансія відкрита й підходить;
  - **жодної вигаданої навички, роботодавця чи цифри** в CV, листі й пості;
  - пост не розкриває зайвих персональних даних.
- Може виправляти тільки видаленням.
- Обробляє помилки інструментів:
  - `needs_input` → відповідає з CV / `candidate.yaml` і повторює `apply`; якщо даних немає, питає людину;
  - `external_apply` → віддає посилання людині;
  - `already_applied` → пропускає;
  - `captcha_required` → просить людину.

**Оркестрація:** Скаут → Перевіряльник; якщо `needs_revision`, ще один раунд Скаута (максимум 2 раунди). Як саме відбувається відправка, визначає політика сайту з `settings.yaml`, а не агент.

**Чому такий розподіл:** головні ризики домену — вигадане в CV і відправка не туди або від чужого імені. Перевіряльник з монопольним правом запису закриває саме ці ризики. Право запису обмежене двічі: на клієнті (інструменту немає в контексті Скаута) і на сервері (`forbidden`).

**Готово, коли:** `cli run --cv cvs/olena.md "..."` у `dry_run` дає заповнені заявки зі скриншотами, а в лозі видно обох агентів і передачу між ними.

## Ризики
- **Справжні заявки справжнім рекрутерам.** Оцінка тільки на `mock` і з `--dry-run`. Справжні відправки — тільки свідомі й поодинокі.
- **Умови користування сайтів.** DOU прямо забороняє автоматичні відгуки, тому за замовчуванням там `manual`. Режим `auto` людина вмикає сама, після попередження, на свій ризик блокування профілю. Для решти сайтів — мала частота і тільки акаунт самого кандидата.
- **Вгадані відповіді у зовнішніх формах.** Агент заповнює тільки те, що є в CV або `candidate.yaml`. Решта повертається як `needs_input`, чутливі питання — тільки від людини.
- **Крихкість селекторів і капчі.** Зрозумілі коди помилок (`form_changed`, `captcha_required`) замість падіння. Бекенд `mock` гарантує, що оцінка не залежить від верстки.
- **Безпека сесій і токенів.** `.browser_profiles/` і `.secrets/` у `.gitignore`. Пароль не проходить через агента.
- **Зміни даних.** Оцінка тільки на знімку, дата фіксована.
- **Ліміти підписки Claude.** Прогін оцінки — це близько 10 запусків, тому запускаємо у фоні й не частіше, ніж потрібно.
- **Ліміт «2–3 інструменти».** Основний сервер `jobs` має рівно 3 інструменти. `linkedin` — окремий сервер-розширення, на презентації це варто пояснити.
